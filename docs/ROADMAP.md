# rag4you-cli — Implementation Roadmap

This roadmap decomposes the larger initiative — a generic, fully-local, configurable, npx-distributable RAG framework with a wizard CLI, decision matrices, MCP integration, and global/project scope — into **5 independently-shippable sub-projects (SP0–SP4)**. Each sub-project gets its own brainstorm → spec → plan → implementation cycle.

## Project intent

Build a generic, language-agnostic, fully-local RAG framework that any user can configure for their project (codebase, docs, library reference). Users define collections in config files; the system handles indexing, search, MCP integration, and incremental reindexing based on the active config. Configuration is wizard-driven (brainstorming-style CLI) and tier-based (small/medium/large model & chunk presets); advanced users can override every default through the config files. The reference implementation that inspired this initiative is the RAG inside `~/Workspace/agent-engineering-toolkit`.

## Sub-projects

| SP | Title | Goal | Deliverable | Depends on | Status |
|---|---|---|---|---|---|
| **SP0** | Baseline benchmark of toolkit RAG | Produce empirical numbers (precision@k, MRR, coverage, token economy) about the current toolkit RAG so SP1 makes data-driven decisions on stack, models, chunk sizes | `bench/` Python package + first `REPORT.md` | none (treats toolkit as black box) | spec drafted (`docs/specs/sp0-baseline-bench.md`) |
| **SP1** | RAG core (pluggable, config-driven) | Generic Python package replacing toolkit's hardcoded `docs`/`code` collections with dynamic schemas, model registry, multi-path support, scope (project vs global), incremental reindex driven by the active config | `rag4you/` Python package | SP0 numbers; reuses `bench/` as regression suite | not started |
| **SP2** | Model catalog & decision matrix | Research and document embedding models per language (Java/TS/JS/Python/...) and per tier (small/medium/large); "Which one to use?" guide with pros/cons, scenarios, expected performance, storage tradeoffs | `docs/MODELS.md`, `docs/CHOOSE.md` | SP0 numbers (informs which models actually work well in the local stack) | not started |
| **SP3** | CLI wizard (npx) | Interactive brainstorming-style wizard (`npx rag4you ...`) for `init` / `add-collection` / `reindex` / `status` / `search`; tiered defaults from SP2 + advanced override; supports project-scope and global-scope databases | npm package wrapping SP1 via subprocess | SP1 stable | not started |
| **SP4** | MCP server (dynamic, scope-aware) | MCP server that derives tools from the active config (one tool per collection) with project-vs-global scope awareness; integration wired by SP3 wizard | `rag4you/mcp/` + integration with SP3 | SP1 stable | not started |

## Conventions

### Plan & spec location
- This file (`docs/ROADMAP.md`): overview of all SPs and their status.
- Per-SP specs: `docs/specs/<sp-id>-<topic>.md` (e.g., `docs/specs/sp0-baseline-bench.md`).
- Per-SP implementation plans (post-spec, generated by `superpowers:writing-plans` skill or in-conversation plan mode): live adjacent to the spec under `docs/specs/`, with suffix `-plan.md` if separated. Both spec and plan live in this repository — never in `~/.claude/plans/` or other out-of-tree locations.

### Process per SP
1. **Brainstorm** — clarify intent, scope, approach (use `superpowers:brainstorming` skill).
2. **Spec** — write to `docs/specs/<sp-id>-<topic>.md`. User approves before implementation.
3. **Plan** — implementation plan (post-spec).
4. **Implement** — TDD where applicable; the bench (SP0) becomes the regression suite for SP1+.
5. **Update this `ROADMAP.md`** — mark the SP done; link to delivered artifacts.

### Scope discipline
Each SP is bounded. Cross-cutting concerns (i18n, locale parity, English-only code convention) are documented in cross-cutting sections of each SP spec, not as a separate SP.

## Cross-cutting requirements (apply to every SP)

- **Code, docs, schemas, comments, commit messages: English only.**
- **CLI user-facing strings: i18n via external `locales/<lang>.yaml` files** (default `en`, initial `pt`, future-extensible by adding new locale files with no code changes).
- **Locale parity rule** (`.claude/rules/locale-parity.md`): every change to a locale file must propagate equivalent changes to all sibling locales in the same commit.
- **Stack-local-by-default:** every new component must work end-to-end with zero API keys / zero cloud calls. Cloud / paid integrations are pluggable extras.
- **All configurable, nothing hard-coded:** every model name, chunk size, top_k, threshold, etc. must be reachable from config files. CLI defaults are the *only* place defaults live; advanced users override via config.
